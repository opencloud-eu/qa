## H5-C1 — Escape does not close the "Set icon" emoji picker (create-space options and Customize > Set icon)

- **Roles:** margaret (Space Admin); any user who can edit a space image.
- **Steps (create modal):**
  1. Spaces > New > New Space, click "Options".
  2. Under "Image" click "Icon" — the "Set icon" picker opens on top of the create modal.
  3. Press Escape (once, twice).
- **Steps (existing space):** right-click an own space tile > Customize > Set icon, press Escape twice.
- **Expected:** Escape closes the topmost modal (like every other OpenCloud modal, e.g. the "Crop image" modal, which does close on Escape).
- **Actual:** the picker stays open after both Escapes (modal count stays 2 in the create flow, 1 on the existing space). The first Escape only blurs the picker's search field and moves focus to `<body>`; the second does nothing. Only the X button closes the picker.
- **Screenshots:** `screens-raw/001-H5-emoji-picker.png`, `screens-raw/002-H5-after-picker-escape.png` (picker still open after Escape), `screens-raw/001-H5-cu-seticon.png`
- **Console errors:** none.
- **Suspected cause:** both callers open `EmojiPickerModal` with `focusTrapInitial: false`
  (`web-app-files/src/components/Modals/CreateSpace/SpaceImagePicker.vue:47`, `web-app-files/src/composables/actions/spaces/useSpaceActionsSetIcon.ts:41`),
  and the emoji-mart picker sets `autoFocus: true` on its search field inside its shadow root
  (`design-system/src/components/OcEmojiPicker/OcEmojiPicker.vue:87`). emoji-mart handles Escape in its search field
  itself and blurs it, so focus ends up on `<body>`, outside the dialog. `OcModal` only listens with
  `@keydown.esc.stop` on the dialog element (`design-system/src/components/OcModal/OcModal.vue:14`), so it never sees Escape.
  A fix could listen for Escape on the document while the modal is active, or keep focus inside the dialog.
- **Known issue check:** `gh issue list -R opencloud-eu/web --search "emoji picker escape"` and `"Set icon modal Escape"` → nothing relevant.
- **Severity guess:** Minor (keyboard cancel path broken; workaround: X button).

## H5-C2 — Hiding disabled spaces keeps a hidden space selected; batch Delete/Enable then acts on a space the user can't see

- **Role:** margaret (Space Admin); any user who can see disabled spaces (space managers).
- **Steps:**
  1. Spaces (Files app, `/files/spaces/projects`), "Show disabled Spaces" on (default).
  2. Tick the checkbox of a disabled space (here `qa-hunt-H5-live-renamed2`). Batch bar: "Edit quota · Enable · Delete — 1 selected".
  3. Open the view options (gear) and switch "Show disabled Spaces" off.
- **Expected:** the space disappears from the list and from the selection (or the toggle clears the selection), so batch actions only work on visible spaces.
- **Actual:** the space disappears from the list, but the batch bar still says "1 selected" and offers Edit quota / Enable / Delete. Clicking Delete opens "Delete Space »qa-hunt-H5-live-renamed2«?" for the invisible space (cancelled in the test).
- **Screenshots:** `screens-raw/003-H5-fs-hidden-selected.png` (list without the space, "1 selected"), `screens-raw/004-H5-fs-delete-modal.png` (delete modal for the hidden space)
- **Console errors:** none.
- **Suspected cause:** `Projects.vue` filters disabled spaces only in the computed list
  (`web-app-files/src/views/spaces/Projects.vue:269-276`), and `setAreDisabledSpacesShown`
  (`web-pkg/src/composables/piniaStores/resources.ts:176`) only flips the flag. Nothing removes the now-hidden ids from
  the selection, so `selectedResources` and the batch actions still include them. (`setAreHiddenFilesShown` at
  `resources.ts:164` has the same pattern for hidden files.) Fix idea: on toggle, drop selected ids that the filter no longer shows.
- **Known issue check:** `gh issue list -R opencloud-eu/web --search "selection hidden disabled spaces"` / `"selected hidden files stay selected"` → nothing.
- **Severity guess:** Minor/Major (destructive batch action on a space the user can't see; the confirm dialog names it, so it is avoidable).
- Reproduced 2x (same result, fresh login each time).

## H5-C3 (Question) — A link to a deleted space silently opens the personal space

- **Role:** margaret.
- **Steps:** create a space, open it (URL `/files/spaces/project/<alias>`), disable and delete it, then open that URL again (bookmark / link shared in chat).
- **Expected:** a "space not found / no access" page, like for a disabled space (which shows "Resource not found … Go to »Spaces Overview«").
- **Actual:** redirect to `/files/spaces/personal/margaret` without any message. The user can't tell the space is gone and may think the link is broken or that the files were moved. Same for any unknown alias.
- **Screenshots:** `screens-raw/002-H5-nav-deep-qa-hunt-h5-dbl.png` (personal space after the deep link)
- **Console errors:** none from the app (only a 404 resource load).
- **Suspected cause:** `DriveResolver.vue:3` renders `drive-redirect` whenever no space matches the alias, and
  `DriveRedirect.vue:39-47` always replaces the route with the personal space (meant for the `personal/home` fake alias).
  Fix idea: only redirect for the fake personal alias / empty alias, otherwise show the not-found state.
- **Known issue check:** `gh issue list -R opencloud-eu/web --search "link deleted space redirects personal"` / `"DriveRedirect"` → nothing.
- **Severity guess:** Question (may be intended; overlaps with H10 deep links).
