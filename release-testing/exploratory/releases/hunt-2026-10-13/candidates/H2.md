Explorer: H2 subagent, user alan, desktop (1440x900), OpenCloud 8.1.0+85466427, web v8.1.0.

## H2-1: One Ctrl+Z restores every item deleted in the last 7 seconds, not only the last deletion

- **Steps:**
  1. As alan, open a folder with `x1.txt`, `x2.txt`, `x3.txt` (`qa-hunt-H2-undo`).
  2. Right-click `x1.txt` → Delete. Toast "x1.txt was moved to trash bin [Undo]".
  3. Within 7 s right-click `x2.txt` → Delete. Second toast "x2.txt was moved to trash bin [Undo]".
  4. Click on an empty area of the file list and press Ctrl+Z (⌘+Z on macOS) once.
- **Expected:** Only the last deletion (`x2.txt`) is undone (like Undo in any editor/file manager; the toast for
  x1 keeps its own Undo button).
- **Actual:** Both `x1.txt` and `x2.txt` are restored by a single key press and both toasts disappear
  (server listing after one Ctrl+Z: x1.txt, x2.txt, x3.txt).
- **Screenshots:** `screens-raw/001-H2-undo-after-del1.png`, `screens-raw/002-H2-undo-after-del2.png`,
  `screens-raw/003-H2-undo-after-ctrlz.png`
- **Console errors:** none.
- **Suspected cause:** every delete binds its own Ctrl+Z handler
  (`packages/web-app-files/src/composables/actions/useFileActionsDeleteResources.ts:111-123`), and the keyboard
  listener runs *all* matching bindings for a key (`packages/web-pkg/src/composables/keyboardActions/useKeyboardActions.ts:125-134`,
  `.filter(...).forEach(action.callback)`). Nothing removes the previous undo binding when a new delete happens.
  Fix idea: keep a single "last undo" binding (remove the previous key action when binding a new one) or only run
  the most recently bound action for a key.
- **Known issue check:** `gh issue list -R opencloud-eu/web --search "undo delete" --state all` → only #1357, #1522,
  #2366 (closed, different). Not reported.
- **Script:** `scripts/H2-04-undo.mjs`
- **Severity guess:** Minor / Question (no data loss, but an unexpected bulk restore).

## H2-2: Restoring a folder together with a file deleted from it earlier fails for the folder; the file lands in a new empty folder

- **Steps:**
  1. As alan, have folder `qa-hunt-H2-rs4` with `qa-hunt-H2-inner.txt` and `qa-hunt-H2-other.txt`.
  2. Delete `qa-hunt-H2-inner.txt`, then delete the folder `qa-hunt-H2-rs4` (both are now in Deleted files → Personal).
  3. In Deleted files → Personal (table view) select both `qa-hunt-H2-rs4` and `qa-hunt-H2-rs4/qa-hunt-H2-inner.txt`
     and click Restore.
- **Expected:** The folder is restored with `qa-hunt-H2-other.txt`, and `qa-hunt-H2-inner.txt` is restored into it
  (the code sorts by path length precisely "to recover the parents first").
- **Actual:** Toasts "qa-hunt-H2-inner.txt was restored successfully" and **"Failed to restore "qa-hunt-H2-rs4""**
  (the trash-bin MOVE of the folder returns HTTP 500). On the server `qa-hunt-H2-rs4` now exists but contains only
  `qa-hunt-H2-inner.txt`; `qa-hunt-H2-other.txt` stays in the trash inside the folder item. Restoring the folder
  again then shows "Folder already exists" (Skip / Replace / Keep both, no merge); Replace puts the just-restored
  folder (with inner.txt) back into the trash. Reproduced twice (rounds rs3, rs4), deterministic.
- **Screenshots:** `screens-raw/002-H2-rs4-selected.png`, `screens-raw/003-H2-rs4-after-restore.png`
  (also `003-H2-rs3-after-restore.png`), follow-up `screens-raw/001-H2-restore-dialog-replace.png`
- **Console errors:** `HTTP 500 .../dav/spaces/trash-bin/<spaceId>/<itemId>` (the folder),
  `Ui: Unknown error at TD.request (worker-*.js)`.
- **Suspected cause:**
  - `packages/web-app-files/src/composables/actions/files/useFileActionsRestore.ts:54-87` (`collectConflicts`):
    the parent `/qa-hunt-H2-rs4` of the file can't be listed (it is still in the trash), so it is added to
    `missingFolderPaths` although that very folder is part of the same restore batch.
  - `packages/web-pkg/src/composables/webWorkers/restoreWorker/worker.ts:80-111`: the restores run in a
    `PQueue({ concurrency: 4 })`, so the sort by path length (`useFileActionsRestore.ts:188`) does not make parents
    restore first. The child task MKCOLs the "missing" parent (`createFolderStructure`, line 86-93) and restores into
    it while the parent's own restore (`overwrite: true`, line 97) runs at the same time and fails.
  - Fix idea: don't treat parents that are in the batch as missing, and restore in path-depth order (await parents
    before children, or restore only the topmost item when a parent is selected together with its children).
- **Known issue check:** `gh issue list -R opencloud-eu/web --search "restore folder"` and opencloud-eu/opencloud
  `"restore trash folder 500"` → nothing matching.
- **Script:** `scripts/H2-05-restore-parent-child.mjs <round>`, follow-up `scripts/H2-06-restore-replace.mjs <folder> replace`
- **Severity guess (H2-2):** Major (restore of a selection partially fails and splits data between files and trash; workaround:
  restore the folder first, then the file).

## H2-3: Upload "Keep both" renames a file to the name of another file in the same upload; that file's content is silently lost

- **Steps:**
  1. As alan, folder `qa-hunt-H2-kb2` contains `c.txt` ("OLD c").
  2. New → Files Upload, select two local files at once: `c.txt` ("NEW c") and `c (1).txt` ("NEW c (1)").
  3. Dialog "File with name »c.txt« already exists" → click **Keep both**.
- **Expected:** `c.txt` (OLD c), `c (1).txt` (NEW c (1)) and the renamed upload `c (2).txt` (NEW c).
- **Actual:** Both uploads go to `c (1).txt` (TUS `Upload-Metadata` name `YyAoMSkudHh0` = "c (1).txt" for both
  POSTs). One POST gets **409**, is retried, and the result is `c (1).txt` = "NEW c". The user's own `c (1).txt`
  ("NEW c (1)") is gone, and the upload panel says **"Upload completed – 2 files uploaded"**. Reproduced twice
  (kb1, kb2).
- **Screenshots:** `screens-raw/001-H2-kb2-after.png` (also `001-H2-kb1-after.png`)
- **Console errors:** `Failed to load resource: the server responded with a status of 409 ()` (TUS POST).
- **Suspected cause:** `packages/web-app-files/src/helpers/resource/actions/upload.ts:171-175` —
  `resolveFileNameDuplicate(fileName, extension, this.resourcesStore.resources)` checks the new name only against the
  files already in the folder, not against the names of the other files in the same upload batch. The same applies to
  folder "Keep both" (line 188). Fix idea: pass `[...resources, ...files.map(f => ({ name: f.name }))]` (and names
  already assigned in this loop) to `resolveFileNameDuplicate`.
- **Known issue check:** `gh issue list -R opencloud-eu/web --search "keep both"` → #3661 describes the same pattern
  for **copy/paste** (`conflictHandling/transfer.ts`), not for upload; #3655 is folder Keep both with special
  characters. Upload variant not reported (could be added to #3661).
- **Script:** `scripts/H2-08-upload-keepboth-batch.mjs <round>`
- **Severity guess:** Major (silent data loss while the UI reports success).

## H2-4: "Retry" after a failed folder creation in a folder upload spins forever and uploads nothing

- **Steps:**
  1. As alan, open `qa-hunt-H2-net`. New → Folder Upload with a local folder `qa-hunt-H2-up2/` containing `top.txt`
     and `sub/f.txt`.
  2. The MKCOL for `qa-hunt-H2-up2` fails (simulated: Playwright route answers MKCOL with HTTP 500; in real life a
     network hiccup or a 5xx).
  3. Upload panel: "Upload failed – 1 of 1 item failed – qa-hunt-H2-up2 – Unknown error". Click the retry icon
     ("Retry all failed uploads"). The network is fine again at this point.
- **Expected:** The folder and its files are uploaded on retry, or the panel says that a folder can't be retried.
- **Actual:** The panel switches to **"Preparing upload..."** with a spinner on `qa-hunt-H2-up2` and stays like that
  (checked after 18 s; no request is sent, nothing is created on the server, `PROPFIND qa-hunt-H2-up2` → 404). The
  close (X) button disappears, so the panel can't be dismissed. A later normal upload (`after-2.txt`) succeeds, but the
  panel then hangs on **"Finalizing upload... Few seconds left"** with the folder still spinning. Reproduced twice
  (up1, up2). (Retry of a failed *file* upload works: `scripts/H2-09-upload-network.mjs 500`.)
- **Screenshots:** `screens-raw/001-H2-fold2-mkcol-1.png` (failed), `screens-raw/003-H2-fold2-mkcol-after-retry-10s.png`
  (stuck), `screens-raw/004-H2-fold2-mkcol-followup.png` (stuck after the next upload)
- **Console errors:** `HTTP 500 .../qa-hunt-H2-net/qa-hunt-H2-up2` (simulated), `Ts: Unknown error at Object.createFolder`.
- **Suspected cause:** when a folder can't be created, `createDirectoryTree` removes all files of that folder from
  Uppy (`packages/web-app-files/src/HandleUpload.ts:409-421`) and only publishes `uploadError` for the folder pseudo
  file. `retryUploads()` in `packages/web-runtime/src/components/UploadInfo.vue:522-536` then raises
  `itemsInProgressCount` / `runningUploads` and calls `uppy.retryAll()`, but Uppy has nothing to retry (the folder is
  not an Uppy file), so no `uploadCompleted` ever brings the counters back. Fix idea: re-run the folder upload
  (MKCOL + its files) on retry, or don't offer retry for folder errors / reset the counters when `retryAll` has no files.
- **Known issue check:** `gh issue list -R opencloud-eu/web --search "retry upload" --state all` → nothing matching.
- **Script:** `scripts/H2-10-folder-upload-mkcol-fail.mjs <round> mkcol`
- **Severity guess:** Minor (re-uploading the folder works; the panel stays stuck until reload).
