## H4-C1 Link role dropdown keeps showing the new role after the update failed

**Reproduced:** 2/2 (request aborted, and server answering 500)

**Steps**
1. alan: folder with a public link of type "Can edit" (password set). Open sidebar > Share.
2. Make `PATCH /graph/v1beta1/drives/{d}/items/{i}/permissions/{id}` fail (network abort or 500).
3. In the link row, open the role dropdown and choose "Can view" (or "Secret File Drop").

**Expected:** Error toast, and the row keeps showing the role the link really has ("Can edit").

**Actual:** Toast "Failed to update link", but the row now shows "Can view" / "Secret File Drop". The server still has
`type: edit`. The wrong label stays until the sidebar is remounted (even other successful edits, e.g. rename, keep the
stale role). The owner thinks the link is read-only while anonymous users can still upload/edit/delete.

**Screenshots:** `screens-raw/001-H4-edit-role-aborted.png`, `screens-raw/001-H4-repro-role-failed.png`

**Console:** `AxiosError: Network Error` / `AxiosError: Request failed with status code 500` (handled, toast shown).

**Suspected cause:** `packages/web-app-files/src/components/SideBar/Shares/Links/ListItem.vue:105` —
`currentLinkType` is a local `ref(linkShare.type)` initialised once and not synced with the prop;
`updateSelectedType` (line 111-121) sets `currentLinkType.value = type` *before* emitting `updateLink`, and
`FileLinks.vue:196-219` (`handleLinkUpdate`) only shows an error on failure, nothing resets the local value.
Fix idea: derive the dropdown value from `linkShare.type` (computed) or revert it on failure.

**Known issue check:** `gh issue list -R opencloud-eu/web --search "link role dropdown failed update"`,
`"public link role revert error"`; opencloud-eu/opencloud `"public link role update failed"` — nothing found.
(H3 reports a similar pattern for user shares: `screens-raw/H3-c1-role-change-failed.png`.)

**Suggested severity:** Minor (only on failed request, but shows wrong permissions).

## H4-C2 Public link can be renamed to a whitespace-only name

**Reproduced:** 2/2

**Steps**
1. alan: sidebar > Share > public link > ⋮ > Rename.
2. Enter `   ` (three spaces). The Save button stays enabled. Save.

**Expected:** Validation error "Link name cannot be empty" (as for an empty field), or the name is trimmed.

**Actual:** Toast "Link was updated successfully"; the server stores `@libre.graph.displayName: "   "`; the link row
shows no name at all (only the role), so the link can no longer be identified in the list.

**Screenshots:** `screens-raw/003-H4-edit-renamed-ws.png`, `screens-raw/003-H4-repro-ws-name.png`

**Console:** none.

**Suspected cause:** `packages/web-app-files/src/components/SideBar/Shares/Links/EditDropdown.vue:177-185` —
`onInput` checks `!name.length`, not `!name.trim().length`; the value is sent untrimmed (line 186-188).

**Known issue check:** `gh issue list -R opencloud-eu/web --search "link name empty whitespace"` — nothing relevant.

**Suggested severity:** Minor.

## H4-C3 Enter in the "Edit password" modal submits an empty / too short password although Confirm is disabled

**Reproduced:** 2/2

**Steps**
1. alan: sidebar > Share > public link with password > ⋮ > Edit password.
2. Leave the field empty (Confirm is disabled) and press Enter in the password field.
   (Same with a 2-character password that violates the policy.)

**Expected:** Nothing is submitted while Confirm is disabled (password policy not met).

**Actual:** `POST .../permissions/{id}/setPassword` is sent with `{"password":""}` (or the too-short value). On this
instance the server rejects it with 400 ("Password protection is enforced" / policy error), so the modal shows the
error. On an instance where the password is **not** enforced for that link type, an empty Enter would remove the
link password (same request as "Remove password") without the user confirming — not verified here because it needs a
global setting change.

**Screenshots:** `screens-raw/005-H4-edit-pw-enter-empty.png`, `screens-raw/004-H4-repro-pw-enter.png`

**Console:** `Failed to load resource: 400` (setPassword).

**Suspected cause:** `packages/web-app-files/src/components/Modals/SetLinkPasswordModal.vue:62-67` — `onKeydownEnter`
emits `confirm` unconditionally; `packages/web-runtime/src/components/ModalWrapper.vue:74-93` (`onModalConfirm`) does
not check `modal.confirmDisabled`. Fix idea: guard in `onKeydownEnter` (or in `onModalConfirm`) on `confirmDisabled`.

**Known issue check:** opencloud-eu/web#2027 "Link password modal can be confirmed without value" (closed 2026-03-26)
fixed the button only; the Enter path is still open → reopen / follow-up rather than a new issue.

**Suggested severity:** Minor (Question: impact on instances without enforcement).

## H4-C4 Owner opening their own file-drop link is not redirected to the folder (fileId query holds the link token)

**Reproduced:** 2/2 (alan logged in, `/s/<token>` of a "Secret File Drop" link)

**Steps**
1. alan creates a "Secret File Drop" link on a folder in Personal.
2. While logged in as alan, open `/s/<token>` and enter the password.
3. For comparison, do the same with a "Can edit" folder link.

**Expected:** Like the folder link (which redirects alan to `/files/spaces/personal/alan/.../folder-edit`), the drop
link resolves to the internal folder for a user who has access — `FilesDrop.vue` has explicit code for this.

**Actual:** alan lands on the anonymous upload page `/files/upload/<token>?fileId=<token>`. The `fileId` query
parameter contains the **link token**, not a file id, so `getPathForFileId` fails (`401 PROPFIND /dav/meta/<token>`)
and the internal redirect never happens. The owner can't see the uploaded files from there.

**Screenshots:** `screens-raw/001-H4-loggedin-alan-BHxo.png` (drop page for owner), `screens-raw/002-H4-loggedin-alan-wwhI.png` (folder link → internal)

**Console:** `401 PROPFIND /dav/meta/<token>` (swallowed).

**Suspected cause:** `packages/web-runtime/src/pages/resolvePublicLink.vue:196-200` pushes
`query: { fileId: unref(publicLinkSpace).fileId }` — `publicLinkSpace` is built from the token only (no dav props),
so its `fileId` falls back to the token. Should be `unref(loadedSpace).fileId`. Consumer:
`packages/web-app-files/src/views/FilesDrop.vue:208-217`.

**Known issue check:** `gh issue list -R opencloud-eu/web --search "file drop logged in"`, `"file drop owner redirect"` — nothing.

**Suggested severity:** Minor / Question (maybe the drop page for logged-in owners is intended, but the code says otherwise).
