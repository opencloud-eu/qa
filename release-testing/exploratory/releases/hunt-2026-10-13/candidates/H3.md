## H3-C1 — Role dropdown shows the new role although the update failed

**Steps**
1. alan: Personal → right-click `qa-hunt-H3-folder` → Share. Share with Lynn Conway as "Can view".
2. Make the next role update fail. Realistic way: keep the panel open while the share is removed elsewhere
   (second tab / API), or the request fails (network, server error).
3. In the "Shared with" list, open Lynn's role dropdown and pick "Can edit".

**Expected:** error toast and the dropdown keeps showing the real role ("Can view").

**Actual:** toast "Error while editing the share." but the dropdown shows "Can edit". The server still has "Can view"
(verified via Graph `GET .../permissions`). Only reopening the panel after a reload shows "Can view" again.
The user sees "Can edit" and has no hint that it was not saved, apart from a toast that disappears.
Seen twice: PATCH aborted via `page.route` (S1) and PATCH answered 500 because the share was deleted elsewhere (S6a).

**Screenshots:** `screens-raw/H3-c1-role-change-failed.png` (aborted PATCH), `screens-raw/*H3-s6a-role-on-deleted*.png` (stale share, 500)

**Console errors:** `AxiosError: Network Error ... at updatePermission ... at updateShare` / `Request failed with status code 500`

**Suspected cause:** `web-app-files/src/components/SideBar/Shares/Collaborators/RoleDropdown.vue:146-149` — `selectRole()`
sets `selectedRole` before emitting `optionChange`; the parent (`Collaborators/ListItem.vue:231-242`, `saveShareChanges`
257-297) catches the error but never resets the dropdown. `selectedRole` is initialised once (line 141) and does not
watch `existingShareRole`, so the store value (unchanged) is not reflected either.

**Side note (same flow, S6a):** removing a share that was already deleted elsewhere → server answers 500 (not 404),
toast "Failed to remove share", and the ghost entry stays in the list until reload. The 500 is server-side.

**Known issue check:** `gh issue list -R opencloud-eu/web --search "share role dropdown error"`, `"role failed permissions share"` — nothing found.

## H3-C2 — Shared with me: "Shares / Hidden Shares" switch does not follow browser Back/Forward

**Steps**
1. lynn: Shares → Shared with me (has at least one hidden and one visible share).
2. Click "Hidden Shares" (URL gets `q_share-visibility=hidden`).
3. Press browser Back.

**Expected:** URL without the param → "Shares" selected and the visible shares listed.

**Actual:** URL is back to `/files/shares/with-me?...` (no `q_share-visibility`), but "Hidden Shares" stays selected and
the hidden shares are still listed. Forward also changes nothing. Reload fixes it.

**Screenshot:** `screens-raw/H3-c2-hidden-filter-after-back.png`

**Console errors:** none.

**Suspected cause:** `web-pkg/src/components/Filters/ItemFilterInline.vue:43,62-71` reads the query only in `onMounted`;
no watcher on `currentRouteQuery`. `web-app-files/src/views/shares/SharedWithMe.vue:146,169-172` keeps
`areHiddenFilesShown` in a local ref that is only set via the `toggleFilter` event.

**Known issue check:** related open issue opencloud-eu/web#3740 ("Filter chips in Favorites, Shared with me and admin
Users stay active after browser Back") — it names `ItemFilter` (share type / shared by chips), not the inline
visibility switch `ItemFilterInline`. Probably same root cause / same fix family → likely **duplicate or extension of #3740**.

## H3-C3 — Shared with me: share disappears live when one of two shares is removed (user still has access via group)

**Steps**
1. alan shares `qa-hunt-H3-file.txt` with lynn (user, Can view) **and** with group `vlsi-lovers` (lynn is a member).
2. lynn has Shares → Shared with me open (the file is listed).
3. alan removes only the user share for lynn (sidebar or API).

**Expected:** lynn still has access through the group share, so the file stays in her "Shared with me" list.

**Actual:** the file vanishes from lynn's list immediately (SSE `share-removed`). Server `GET /me/drive/sharedWithMe`
still returns the file, and after a reload it is listed again. Reproduced twice (S5, two runs).

**Screenshot:** `screens-raw/H3-c3-group-share-removed-live.png` (only the folder is left; file is gone)

**Console errors:** none.

**Suspected cause:** `web-runtime/src/container/sse/shares.ts:300-306` (`onSSEShareRemovedEvent`) removes the resource
by `fileId === sseData.itemid` without checking whether the user still has another share on that item (re-fetch
`listSharedWithMe` like `onSSEShareCreatedEvent` does at 158-173). The FIXME at line 253 notes a similar group case for
the files view.

**Known issue check:** web: `"shared with me group share removed sse"`, `"share revoked group"`; opencloud:
`"shared with me disappears group"` — nothing found.

## H3-C4 — Enable/Disable sync on a mixed selection fails with an error and leaves the selection

**Steps**
1. lynn has two incoming shares: `qa-hunt-H3-folder` (synced) and `qa-hunt-H3-file.txt` (sync disabled).
2. Shared with me (list view): select both. The batch bar offers both "Enable sync" and "Disable sync".
3. Click "Enable sync" (or "Disable sync").

**Expected:** the action is applied to the shares where it makes sense (the unsynced / synced one), success message,
selection cleared.

**Actual:** the server call for the share that is already in the target state fails with 409 `nameAlreadyExists`
(POST `/drives/<jail>/root/children` for enable, DELETE `.../items/<id>` for disable). The UI shows
"Failed to enable sync for the selected shares" / "Failed to disable sync for the selected shares", both rows stay
selected — although the other share was in fact changed on the server (verified via `sharedWithMe`).
Reproduced: enable twice (S8, S9c), disable once (S9b).

**Screenshots:** `screens-raw/*H3-s8-mixed-enable*.png`, `screens-raw/*H3-s9-mixed-disable*.png`, `screens-raw/*H3-s9-mixed-enable*.png`

**Console errors:** `AxiosError: Request failed with status code 409`

**Suspected cause:** `web-app-files/src/composables/actions/files/useFileActionsEnableSync.ts:35-57` iterates over
all `resources` instead of only `!resource.syncEnabled` (the action is visible when *some* need it, line 100);
same in `useFileActionsDisableSync.ts:35-54` (visible when some are synced, line 98, but runs on all).

**Known issue check:** `"enable sync selected shares"`, `"sync share batch"` — nothing found.

## Not new / duplicates

- **Shared with others: adding a user share from the sidebar drops the selection and empties the sidebar**
  (sidebar shows "Select a file or folder" right after "Share was added successfully"; list reloads via
  `GET /me/drive/sharedByMe`). Reproduced 3x (S10, `screens-raw/*H3-s10a-after-share-click*.png`).
  Cause `web-app-files/src/views/shares/SharedWithOthers.vue:217-235` (`loadResourcesTask.perform()` not awaited,
  re-select against the old list). **Duplicate of opencloud-eu/web#3669** (reported for links; same code path for
  user/group shares — worth a comment on #3669 that it also happens when adding a user/group share).

## Observations (not candidates)

- Sharing with several recipients where one invite fails: the successful one is added, a per-recipient error toast is
  shown, and the failed recipient is removed from the form too (user has to search again).
  `InviteCollaboratorForm.vue:480-481` clears `selectedCollaborators` unconditionally. UX choice, not filed.
- In a project space, `InviteCollaboratorForm.vue:442-446` calls `getDrive` after the invites without try/finally —
  if it fails, `saving` would stay `true` (button disabled, spinner). Not tested (alan cannot create spaces; H5 area).
- Server: PATCH/DELETE of a permission that no longer exists answers **500** instead of 404 (see C1 side note).
- "Cannot access" (deny) works for a subfolder of a shared folder: lynn gets 404 on the subfolder, not listed. OK.
- Live revoke while the recipient is inside the share: toast "Your access to this share has been revoked" appears
  (short-lived, ~5 s); list stays stale until navigation, reload shows "Resource not found". OK by design.

## Coverage

Tried: share user/group via sidebar (search, Enter key, role pick, expiration in create form), double click on Share
(1 request only), role change (incl. failing PATCH, stale share deleted elsewhere), Cannot access on file and subfolder,
expiration set/edit/remove via edit dropdown (server verified), remove share (personal view, Shared with others view,
already-deleted share), Shared with me: hide/unhide, Hidden Shares switch with Back/Forward, enable/disable sync single
and mixed selection, live updates (SSE) for share created / removed / user+group overlap / revoke while inside,
deep link after revoke, recipient with Can edit (no reshare action offered, upload works), switching resource while the
share form has a pending recipient (form resets — OK), multi-recipient with one failing invite.

Not covered: pagination of >10 collaborators, external (OCM) share type (not enabled), guest invite (not on instance),
project-space member sharing (H5), share expiry reaching its date (needs waiting), mobile viewport, keyboard-only
navigation inside the role dropdown, Shared with me "Shared By"/"Share Type" filters (covered by #3740).
