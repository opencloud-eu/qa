Restoring a folder together with a file deleted from it earlier fails for the folder; data ends up split between folder and trash

## Steps to reproduce
1. Folder `rs4` with `inner.txt` and `other.txt`.
2. Delete `inner.txt`, then delete `rs4`.
3. In Deleted files select both `rs4` and `rs4/inner.txt` and click Restore.

## Actual
"inner.txt was restored" and "Failed to restore rs4" (trash MOVE → HTTP 500). `rs4` now exists but contains only `inner.txt`; `other.txt` stays in the trash. Restoring the folder again → "Folder already exists" without merge; Replace puts the just-restored folder back into the trash.

## Expected
The folder is restored with `other.txt`, and `inner.txt` into it (the code sorts by path length "to recover the parents first").

## Cause (web v8.1.0)
`packages/web-app-files/src/composables/actions/files/useFileActionsRestore.ts:54-87` treats the parent as missing although it is in the same batch, and `packages/web-pkg/src/composables/webWorkers/restoreWorker/worker.ts:80-111` restores with `PQueue({ concurrency: 4 })`, so parents are not restored first; the child MKCOLs the parent while the parent restore (`overwrite: true`) fails.

## Fix idea
Don't treat parents in the batch as missing and restore in path-depth order (or only the topmost item).

## Environment
OpenCloud 8.1.0+85466427 (rolling), web 8.1.0, Chromium (Playwright), alan, desktop. Found in the exploratory bug hunt of 2026-10-13 (opencloud-eu/qa, `exploratory/releases/hunt-2026-10-13`), finding H2-2, reproduced 2/2.
