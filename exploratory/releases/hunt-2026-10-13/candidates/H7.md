# H7 — Search: candidates

## H7-C1 Results page spins forever when the search request takes longer than ~0.5 s and the search bar starts a preview search

**Steps**
1. Log in as alan, open Personal.
2. Click into the top-bar search field, type `qa-hunt-H7-alpha` and press Enter right away (within 500 ms of the last key stroke).
3. The search request is slower than ~500 ms (simulated with a 1 s delay on the REPORT request; realistic for a big full-text index or a slow network).

Alternative trigger: on a results page whose search request is still running (e.g. after a reload with a slow server), click into the search field (the term is restored from the URL, so `showPreview()` starts a preview search).

**Expected:** the results page shows the matching file.

**Actual:** the results page shows the loading spinner forever (checked after 8 s and 13 s). Network log: the list REPORT (limit 200) is sent, ~400 ms later the preview REPORT (limit 8) is sent and the list REPORT is aborted (`net::ERR_ABORTED`). Nothing retries. Reproduced 2/2 with Enter-right-away (1 s delay), 1/1 with click-into-search-bar (4 s delay). Without delay the list request finishes before the preview fires, so the bug is timing-dependent; the preview REPORT is still sent after every quick Enter (wasted request).

**Screenshots:** `screens-raw/001-H7-04-enter-fast-d1000-run1.png`, `screens-raw/002-H7-04-enter-fast-d1000-run2.png`, `screens-raw/002-H7-03-race-after-13s.png`

**Console errors:** none (the cancellation is swallowed).

**Suspected cause:**
- Preview and list search share one restartable task: `packages/web-app-files/src/extensions.ts:41` creates one `useSearch()` and passes the same `searchFunction` to `Preview` and `List` (`search/sdk/index.ts:27-28`); `useSearch.ts:38-86` is `.restartable()`, so any preview search cancels a running list search.
- `packages/web-app-search/src/views/List.vue:37-40` returns on `'cancel'` without resetting `loading`, so the spinner stays.
- `packages/web-app-search/src/portals/SearchBar.vue:306-313` cancels the debounced preview search on Enter only when the results page is already active; when Enter is pressed from any other page, the debounced `search()` (500 ms, line 384) still fires after the navigation.
- Script: `scripts/H7-04-enter-fast.mjs 1000 2`, `scripts/H7-03-race.mjs race`.

**Known issue check:** `gh issue list -R opencloud-eu/web --search "search spinner"`, `"search results loading"`, `"search cancel preview results page"`: nothing matching. Related but different: web#3663 (preview stays on "Searching…" when the request fails, closed).

## H7-C2 After renaming or deleting a folder in the search results, its descendants stay with a stale path; actions on them fail

**Steps**
1. alan has `qa-hunt-H7-root/qa-hunt-H7-other/qa-hunt-H7-gamma.txt`.
2. Search for `qa-hunt-H7-` and open the results page (list view). Both the folder `qa-hunt-H7-other` and the file `qa-hunt-H7-gamma.txt` are listed.
3. In the results, rename the folder `qa-hunt-H7-other` to `qa-hunt-H7-other3` (context menu → Rename). Succeeds.
4. In the same results list, rename `qa-hunt-H7-gamma.txt` to `qa-hunt-H7-gamma-r2.txt`.

**Expected:** gamma is renamed; its row shows the new parent folder name.

**Actual:** gamma's row still shows the old parent folder name (its resource keeps the old path). Renaming it fails with "Failed to rename "qa-hunt-H7-gamma.txt" to »qa-hunt-H7-gamma-r2.txt«"; the web sends `MOVE /dav/spaces/<space>/qa-hunt-H7-root/<old folder name>/qa-hunt-H7-gamma.txt` → 404. Server state: file unchanged. The same stale path is used by every path-based action on those rows (rename, and by the same mechanism delete/move/copy/download). The parent-folder link under the row first PROPFINDs the old path (404) and only recovers through the fileId. Reproduced 2/2 (runs with other2→other3 and other3→other).

**Variant — delete:** delete folder `qa-hunt-H7-mvdir` (or `qa-hunt-H7-deldir`) from the results. The folder row disappears ("moved to trash bin"), but its child `qa-hunt-H7-child.txt` / `qa-hunt-H7-delchild.txt` stays in the results. Clicking it opens the text editor with "Resource not found" (PROPFIND 404); deleting it from the results shows "Failed to delete "qa-hunt-H7-delchild.txt"". Reproduced 2/2 (`scripts/H7-11-move-delete.mjs`, `scripts/H7-12-delete-parent.mjs`). (Moving a single file via "Move to" from the results updates its row correctly.)

**Screenshots:** `screens-raw/001-H7-07-child-rename-run1.png`, `screens-raw/001-H7-07-child-rename-run2.png`, `screens-raw/003-H7-06-renamed-parent.png` (stale parent name under gamma), `screens-raw/005-H7-11-open-child-of-deleted.png`, `screens-raw/002-H7-12-delete-child-of-deleted.png`

**Console errors:** `Ts: Resource ./qa-hunt-H7-root/qa-hunt-H7-other3/qa-hunt-H7-gamma.txt not found`, three 404s.

**Suspected cause:** `packages/web-app-files/src/composables/actions/files/useFileActionsRename.ts:54-104` updates only the renamed resource in the resources store (`upsertResource`). In a normal folder view no descendants are in the store, but the search results list (`components/Search/List.vue:463-469` → `initResourceList`) holds descendants with their absolute `path`, which are left stale. Delete likewise removes only the selected resources from the store. Fix idea: after renaming/moving/deleting a folder, drop or rewrite the `path` of store resources whose path starts with the old folder path (or re-run the search on the results page).

**Known issue check:** `gh issue list -R opencloud-eu/web --search "search results rename folder path"` and `"stale path after rename"`: nothing matching.

## H7-C3 Tag filter returns wrong results for a tag that contains "+"

**Steps**
1. alan tags `qa-hunt-H7-gamma.txt` with `qa-hunt-H7-x+y` and `qa-hunt-H7-dup.txt` with `qa-hunt-H7-x` (tags with `+` are accepted by the server and listed in the Tags filter).
2. Search for `qa-hunt-H7-`, open the results page, open the **Tags** filter and select `qa-hunt-H7-x+y`.
3. Reload the page.

**Expected:** only `qa-hunt-H7-gamma.txt` (tagged `qa-hunt-H7-x+y`) is listed, the chip shows `qa-hunt-H7-x+y`.

**Actual:** only `qa-hunt-H7-dup.txt` (tagged `qa-hunt-H7-x`) is listed; gamma is missing. The chip shows `qa-hunt-H7-x` (after selection and after reload). The server itself answers correctly for `tag:"qa-hunt-H7-x+y"` (returns gamma), so the web builds the wrong query. Reproduced 2/2 (selection + reload).

**Screenshots:** `screens-raw/001-H7-08-tag-plus.png`, `screens-raw/002-H7-08-tag-plus-reload.png`

**Console errors:** none.

**Suspected cause:** multiple selected items are stored in the query param joined by `+` without escaping (`packages/web-pkg/src/components/ItemFilter.vue:139-152`) and split again on `+` (`ItemFilter.vue:225` for the chip, `packages/web-pkg/src/composables/search/useSearch.ts:129` for the KQL `tag:(...)`). A tag containing `+` is split into `qa-hunt-H7-x` OR `y`. Fix idea: encode each id (or use a repeated query param / a separator that can't occur in tags).

**Known issue check:** `gh issue list -R opencloud-eu/web --search "tag filter plus"`, opencloud `"tag search special characters"`: nothing matching.

## H7-C4 Location filter ("Current folder" / "All files") is not synced with the URL after browser Back/Forward

**Steps**
1. Open `qa-hunt-H7-root/qa-hunt-H7-sub`, type `qa-hunt-H7-` with location "All files", press Enter → 23 results, chip "All files" (`useScope=false`).
2. Switch the location filter in the search bar to "Current folder" → 2 results (`useScope=true`).
3. Press browser Back.

**Expected:** 23 results and the location chip shows "All files".

**Actual:** URL `useScope=false`, 23 results, but the chip still shows **"Current folder"**. The chip and the results disagree; the next search typed into the bar uses the chip's state, not the visible results' scope. Reproduced 2/2.

**Screenshots:** `screens-raw/001-H7-10-loc-after-back-run1.png`, `screens-raw/001-H7-10-loc-after-back-run2.png`

**Console errors:** none.

**Suspected cause:** `packages/web-pkg/src/components/SearchBarFilter.vue:93-133` only watches `currentFolderUsable`, never the `useScope` route query after the first run; `packages/web-app-search/src/portals/SearchBar.vue:180` `locationFilterId` is only changed by `onLocationFilterChange` (line 351), not by route changes.

**Known issue check:** web#3664 / web#3740 and open PR web#3699 cover the `ItemFilter` / `ItemFilterToggle` chips (Type, Tags, Last modified, Title only) — not the `SearchBarFilter` location filter. (The tag chip on the results page also stays active after Back — that part is web#3664, not re-reported.) `gh issue list -R opencloud-eu/web --search "search location filter current folder"`: nothing matching.
