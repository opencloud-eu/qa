## H6-C1 — App URL of a file opened by another user who has access to it shows a raw TypeError

**Severity guess:** Major (copying the browser URL of an open file is the common way to send a file; no meaningful message, no fallback)

**Steps**
1. alan shares folder `qa-hunt-H6` with lynn (Can edit).
2. alan opens `qa-hunt-H6/qa-hunt-H6-doc.md` in the Text Editor (or an image in Preview) and copies the URL from the address bar, e.g.
   `/text-editor/personal/alan/qa-hunt-H6/qa-hunt-H6-doc.md?fileId=<id>&contextRouteName=files-spaces-generic&...`
3. lynn opens that URL.

**Expected:** The file opens for lynn (the URL contains the `fileId`, which lynn can access through the share; `/f/<fileId>` resolves to `/text-editor/share/qa-hunt-H6/...` fine), or at least a clear "not found / no access" message.

**Actual:** The app area shows only `Cannot read properties of undefined (reading 'webDavPath')`. Same for Preview (`/preview/personal/alan/...`). Also for any other path in a drive the user cannot resolve (`/text-editor/personal/alan/<nonexistent>.md` as lynn) - alan himself gets the proper "Resource not found" screen for the same URL.

Related variant (same root): a deep link with only `fileId` works for text-editor and pdf-viewer (`/text-editor?fileId=<id>` resolves the path), but `/preview?fileId=<png id>` shows `Cannot read properties of null (reading 'webDavPath')` — for alan as owner too.

**Screenshots:** `screens-raw/001-H6-ownerurl-lynn-editor.png`, `screens-raw/002-H6-ownerurl-lynn-preview.png`, `screens-raw/003-H6-ownerurl-lynn-permalink.png` (permalink works), `screens-raw/002-H6-deep-lynn-md-wrong-path.png`, `screens-raw/007-H6-deep-alan-png-preview-only-fileId.png`

**Console:** `TypeError: Cannot read properties of undefined (reading 'webDavPath')` (lynn); `TypeError: Cannot read properties of null (reading 'webDavPath')` (preview with fileId only).

**Suspected cause**
- `web-pkg/src/composables/appDefaults/useAppDefaults.ts:52-60`: `useDriveResolver` cannot resolve `personal/alan` for lynn, `space` stays undefined; the file context has no space.
- `web-pkg/src/components/AppTemplates/AppWrapper.vue:351-355`: the `fileId` fallback (`addMissingDriveAliasAndItem`) only runs when `driveAliasAndItem` is empty, not when it cannot be resolved; then `getFileInfo` dereferences the missing space and the raw error message is rendered via `ErrorScreen` (`AppWrapper.vue:406-409`).
- Preview variant: preview emits `update:resource`, so `noResourceLoading` is true and the watcher at `AppWrapper.vue:472-507` skips `loadResourceTask` (and with it `addMissingDriveAliasAndItem`) entirely.

**Known issue check:** `gh issue list -R opencloud-eu/web --search "webDavPath"`, "preview fileId deep link", "Cannot read properties of undefined app URL shared" — nothing matching. opencloud repo: nothing.

**Reproduced:** 2x (H6-16 as lynn, H6-21 as lynn; preview-fileId 2x as alan and lynn).

## H6-C2 — Deleting a file from inside the text editor with unsaved changes: the file is deleted first, then "Save" fails with a misleading "updated outside this window" error and the user is stuck in the editor of a deleted file

**Severity guess:** Minor (no data loss on disk because the file goes to the trash and Undo exists; but the unsaved changes cannot be saved and the flow is confusing)

**Steps**
1. alan opens `qa-hunt-H6/qa-hunt-H6-del.md` in the Text Editor.
2. Types some text (unsaved, Save button enabled).
3. Top bar ⋮ → Delete.
4. The "Unsaved changes — Do you want to save them?" dialog appears. Click **Save**.

**Expected:** Either a warning before deleting a file with unsaved changes, or, once deleted, closing without offering a save that cannot succeed. At least the error should say the file was deleted.

**Actual:** The file is already moved to the trash (WebDAV GET 404) when the dialog appears. "Save" → PUT with If-Match → 412 → toast "This file was updated outside this window. Please copy your changes, save the file under a new name (»Save As...«) or reload…". The dialog closes, the editor stays open on the deleted file, still dirty. Server: file stays deleted (404).

**Screenshots:** `screens-raw/001-H6-edel-modal.png`, `screens-raw/002-H6-edel-after-save.png`

**Console:** `Failed to load resource: 412`, `ws: This file was updated outside this window…`

**Suspected cause**
- `web-pkg/src/components/AppTemplates/AppWrapper.vue:893-895` (`onDelete:resource`) and the Delete entry in the top bar menu (`AppWrapper.vue:765-767`) run the delete action without checking `isDirty`.
- `AppWrapper.vue:737-751` (`onDeleteResourceCallback`) calls `closeApp()`, which hits `onBeforeRouteLeave` (`AppWrapper.vue:819-843`) and offers "Save" for a resource that no longer exists.
- `AppWrapper.vue:573-578`: every 409/412 is reported as an external update, also when the file is gone.

**Known issue check:** searched "editor delete unsaved changes", "deleted file editor open" — not found (#592 is the original story for delete in app wrapper).

**Reproduced:** 2x (H6-12 run twice).

## H6-C3 — Text editor and preview open any resource type from a deep link (folder → blank editor, PNG → editable binary garbage; .md in preview shows a different file)

**Severity guess:** Minor (needs a hand-made / stale URL; PNG case can corrupt the file if the user types and saves)

**Steps / actual** (as alan, owner):
- `/text-editor/personal/alan/qa-hunt-H6?fileId=<folder id>` → editor chrome with folder icon and name "qa-hunt-H6", empty editor, save button, no error (`screens-raw/004-H6-deep-alan-folder-in-editor.png`).
- `/text-editor/personal/alan/qa-hunt-H6/qa-hunt-H6-img1.png?fileId=<png id>` → PNG bytes shown as text in an editable plain-text editor (`screens-raw/005-H6-deep-alan-png-in-editor.png`); a save would overwrite the image with the re-encoded text.
- `/preview/personal/alan/qa-hunt-H6/qa-hunt-H6-doc.md?fileId=<md id>` → page title "Preview for qa-hunt-H6-doc.md", but the stage shows `qa-hunt-H6-img1.png` (first image in the folder) (`screens-raw/006-H6-deep-alan-md-in-preview.png`).

**Expected:** An error like "This file type cannot be opened with <app>" (or redirect to the default app), no editable binary.

**Suspected cause:** `AppWrapper.vue:413-465` (`loadFileTask`) never checks that the resource is a file and that its extension/mime type is registered for `applicationId`; `web-app-preview/src/App.vue:417-431` (`setActiveFile`) silently falls back to index 0 when the fileId is not among the media files.

**Known issue check:** #3382 (text editor for files without extension) is a feature request, not this. Nothing else found.

**Reproduced:** 1x as alan (H6-16), the folder/PNG/md cases as lynn ran into C1 instead.

## H6-C4 (Question) — Video/audio opened from the file list never autoplays although the preview app is meant to autoplay the first item

**Steps:** Upload a `.webm` (silent), click it in the file list.
**Actual:** `<video autoplay>` is false, video paused (`screens-raw/001-H6-video.png`).
**Expected (from code intent):** `isAutoPlayEnabled` starts as `true`, and only manual navigation should switch it off.
**Suspected cause:** `web-app-preview/src/App.vue:468-482` — the `activeMediaFile` watcher is not `immediate`, so on the first run `oldValue` is `undefined`, the check `oldValue !== null` is true and autoplay is switched off before the first video mounts. Probably intended `oldValue != null` / `!== undefined`.
**Known issue check:** "autoplay video preview" — none.
**Reproduced:** 2x (H6-22 run twice). Headless Chromium; browser autoplay policy may block audio anyway, but here the attribute itself is never set.

## Observations (not candidates)
- Save failure because of a network error shows a toast "An error occurred" with no description (`AppWrapper.vue:612-613`, `new HttpError('', …)`); state is kept dirty and a retry works (`screens-raw/001-H6-net-abort.png`).
- After a conflict ("updated outside this window"), the persistent error toast covers the "Save" button of the Save-as dialog that the toast recommends (`screens-raw/002-H6-saveas-modal.png`); closing the toast is a workaround.
- In a collaborative session, "Don't Save" by one user does not discard the edits: they stay in the shared Yjs doc and the other user is dirty with them (by design of the room).
- Markdown save re-formats tables and adds blank lines (stable, no accumulation); many markdown round-trip issues are already filed (#3622, #3625, #3754, #3755 …).
- PDF viewer shows "This PDF could not be displayed in your browser" in headless Chromium (no PDF plugin) — environment, not tested further.
