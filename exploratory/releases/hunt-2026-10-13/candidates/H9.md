## H9-1 "Mark all as read" clears the notification list even when the request fails

- **Steps**
  1. Log in as alan (with at least one notification in the bell).
  2. Make `DELETE /ocs/v2.php/apps/notifications/api/v1/notifications` fail (offline / server error; in the test the request was aborted with `page.route`).
  3. Open the bell, click **Mark all as read**.
  4. Reload the page.
- **Expected:** an error message; the notifications stay in the list (they were not marked read on the server).
- **Actual:** the list switches to "Nothing new" and the badge disappears, no error is shown. The server still has
  all notifications (6), and after a reload the badge shows 6 again.
- **Screenshot:** `screens-raw/002-H9-notif-after-aborted-markall-64030.png`, after reload `screens-raw/003-H9-notif-after-reload-67246.png`
- **Console:** `AxiosError: Network Error ... at Cl.delete`
- **Suspected cause:** `packages/web-runtime/src/components/Topbar/Notifications.vue` `deleteNotificationsTask`:
  the list is filtered in `finally`, i.e. also on error, and the `catch` only logs to the console (no `showErrorMessage`).
- **Known issue check:** `gh issue list -R opencloud-eu/web --search "notifications"` / "mark all as read" — nothing matching.
- Reproduced: 1x (script `scripts/H9-06-notif.mjs`).

## H9-2 A notification received live disappears again when the initial notifications request finishes later

- **Steps**
  1. Log in as alan. Slow down the notifications list request (`GET .../apps/notifications/api/v1/notifications`;
     in the test: response taken from the server immediately, delivered after 10 s — like a slow connection/server).
  2. Reload the page. While the request is still pending, mary shares a folder (`qa-hunt-H9-n4`) with alan.
  3. The share notification arrives via SSE and shows up in the bell (badge 1, item visible).
  4. Wait until the slow list request finishes.
- **Expected:** the live notification stays (the list merges the server list with notifications received meanwhile).
- **Actual:** when the older list response arrives it replaces the whole list; the live notification is gone from the
  bell although it is still on the server (server count 1, UI count 0). It only comes back after a reload.
- **Screenshots:** before `screens-raw/001-H9-notif-race-n4-before-86881.png`, after `screens-raw/002-H9-notif-race-n4-after-92997.png`
  (first run: `screens-raw/002-H9-notif-race-n2-49665.png`)
- **Console:** none.
- **Suspected cause:** `Notifications.vue` `fetchNotificationsTask` assigns `notifications.value = data` and so drops
  everything `onSSENotificationEvent` prepended while the request was in flight. Related: SSE items are not deduplicated
  by `notification_id` (`onSSENotificationEvent` always prepends), and the list uses `:key="index"`. During the probe the
  bell once showed "Margaret Hamilton deleted Space qa-hunt-H5-create3" twice (`screens-raw/001-H9-notif-drop-62403.png`),
  which was not reproducible on purpose.
- **Known issue check:** "notification duplicate", "notifications" — nothing matching.
- Reproduced: 2x (n2, n4; scripts `H9-07-notif-live.mjs`, `H9-08-notif-race.mjs`). Without the delay (n1, n3, n5–n8) it works.

## H9-3 Create app token: after a failed request, focus leaves the modal and Escape no longer closes it

- **Steps**
  1. Account → App Tokens → **New**, enter a note `qa-hunt-H9-c` and an expiration date.
  2. Make `POST /auth-app/tokens` fail (aborted in the test). Click **Confirm**.
  3. The toast "An error occurred while creating the app token." appears. Press **Escape**.
- **Expected:** focus stays in the modal; Escape closes it (as it does before the request and after a successful create).
- **Actual:** focus is on the **New** button behind the modal backdrop (`document.activeElement` = `create-app-token-btn`);
  Escape does nothing, the modal stays open. Only the X button closes it. Keyboard users are stuck outside the dialog.
- **Screenshot:** `screens-raw/004-H9-tok-C-abort-75327.png`
- **Console:** `AxiosError: Network Error` (expected for the aborted request).
- **Suspected cause:** `packages/web-runtime/src/components/Modals/AppTokenModal.vue` `createAppToken`: the confirm button
  gets `disabled` (`isConfirmDisabled` includes `isCreating`) and the modal `isLoading` while the request runs, so the
  focused button loses focus; nothing restores it to the modal afterwards.
- **Known issue check:** "app token" — only the fixed #3692 (reload) and the cancel-while-creating fix; nothing about focus.
- Reproduced: 2x (scripts `H9-03-tokens.mjs`, `H9-04-tokens2.mjs`). Severity guess: Minor.

## H9-4 App token note accepts whitespace only

- **Steps:** App Tokens → New, note = three spaces, any expiration date.
- **Expected:** "The note is required" (as for an empty note) / Confirm disabled.
- **Actual:** Confirm is enabled; the token would be created with a blank note (the list then shows an empty note
  instead of `-`).
- **Screenshot:** n/a (checked via `isDisabled()` in `H9-04-tokens2.mjs`)
- **Suspected cause:** `AppTokenModal.vue` `isConfirmDisabled` uses `!unref(tokenLabel)` without `trim()`.
- Severity guess: Minor / Question.
