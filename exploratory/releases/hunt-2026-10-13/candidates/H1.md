## H1-C1 Dragging an unselected item also moves every item that was selected before

- **Steps**
  1. Folder with files `a.txt`, `b.txt` and a folder `target` (table view).
  2. Click the row of `a.txt` (e.g. the size cell) so that only `a.txt` is selected ("1 selected").
  3. Drag `b.txt` (not selected) and drop it on `target`.
- **Expected:** only the dragged item `b.txt` is moved (common file-manager behaviour: dragging an unselected item drags
  only that item and replaces the selection). At least the drag ghost should make clear that several items are moved.
- **Actual:** `a.txt` **and** `b.txt` are moved into `target`, without any notice. Server state (WebDAV PROPFIND of
  `target`): `["qa-hunt-H1-a.txt","qa-hunt-H1-b.txt"]`. Reproduced 3/3 (second run: `b.txt` selected, `c.txt` dragged ->
  both moved). Third, very natural variant (in a share where alan is editor, `H1-20-live-two-users.mjs`): alan renames
  `s2.txt` via its right-click menu (right-click selects the row), then drags `s1.txt` onto folder `sub` — the just
  renamed `s2-renamed.txt` silently moves into `sub` as well (lynn's folder listing via WebDAV: `sub` contains
  `s1.txt` and `s2-renamed.txt`).
- **Screenshots:** `screens-raw/001-h1-05-a-selected.png` (only a.txt selected), `screens-raw/002-h1-05-after-drag-b.png`
  (a.txt and b.txt gone), `screens-raw/001-h1-06-repro-after-drag-c.png`.
- **Console errors:** none.
- **Suspected cause:** `packages/web-pkg/src/composables/resources/useResourceViewDrag.ts:32-38` — `dragStart` calls
  `resourcesStore.toggleSelection(resource.id)` when the dragged item is not selected, which *adds* it to the existing
  selection; `GenericSpace.vue:441-506` (`fileDropped`) then moves the whole `selectedResources`. Fix idea: if the
  dragged item is not selected, replace the selection with it (`setSelection([resource.id])`).
- **Known issue check:** `gh issue list -R opencloud-eu/web --search "drag selected moved"` / `"drag and drop"` — only
  #3659 (desktop files dropped on breadcrumb), not this one. Nothing in opencloud-eu/opencloud.
- **Severity guess:** Minor/Major (unintended data move, no confirmation; undo via Move back).

## H1-C2 A failed drag & drop move shows no error at all (e.g. locked file -> HTTP 423)

- **Steps**
  1. Lock a file (`a.txt`) — e.g. it is open in Collabora, or via WebDAV `LOCK` (used here).
  2. In the files table drag `a.txt` and drop it on folder `plain`.
- **Expected:** an error message like the one for cut/paste ("Failed to move »a.txt« … the file is locked"), or the
  drag is not allowed for a locked file (the "Move to" action is hidden for locked files).
- **Actual:** the server answers `MOVE` with **423 Locked**, the UI shows **nothing** — no message, the file just stays
  where it is. Same with any other server error (mocked 500: no message for drag & drop, while cut + Ctrl+V of the same
  file shows "Failed to move »qa-hunt-H1-c.txt«"). Reproduced 2/2 (423 real, 500 mocked).
- **Screenshots:** `screens-raw/002-h1-08-locked-after-drag.png` (locked file still in place, no message),
  `screens-raw/001-h1-07-status-drag.png` (500, no message) vs `screens-raw/002-h1-07-status-paste.png` (paste shows
  the error).
- **Console errors:** only the worker log `Ui: move: error: locked by urn:uuid:…` (console.error in the paste worker).
- **Suspected cause:** `packages/web-app-files/src/views/spaces/GenericSpace.vue:502-505` — the `startWorker` callback
  of `fileDropped` ignores `failed` and never calls `resourceTransfer.showResultMessage(failed, successful, …)` (which
  paste `useFileActionsPaste.ts:84` and Move-to `useFileActionsMove.ts:76` do). Also no `locked` guard for the dragged
  resources (Move-to has one: `useFileActionsMove.ts:227`).
- **Known issue check:** `gh issue list -R opencloud-eu/web --search "drag and drop"` — not reported.
- **Severity guess:** Minor.

## H1-C3 Cut + paste (or copy/move) that fails with a network error reports nothing and empties the clipboard

- **Steps**
  1. Select `c.txt`, press Ctrl+X, open folder `plain`, press Ctrl+V while the `MOVE` request fails at network level
     (connection reset/offline; simulated with `context.route(... MOVE ...).abort()`).
- **Expected:** "Failed to move »c.txt«" (as for an HTTP error) and the clipboard keeps the item so the user can retry.
- **Actual:** no message at all, the loading indicator ends, nothing is moved, and the clipboard is cleared (Paste is gone),
  so the user does not learn that the cut/paste didn't happen. Same for drag & drop. Reproduced 2/2 (paste and drag in the
  same run, two runs of the script with `abort`).
- **Screenshots:** `screens-raw/004-h1-06-aborted-move.png` (drag), and run `H1-07-move-fail.mjs abort` (paste; no
  notification in the DOM).
- **Console errors:** `TypeError: Cannot read properties of undefined (reading 'text') at TD.request (worker-….js)`.
- **Suspected cause:** two chained errors —
  `packages/web-client/src/webdav/client/dav.ts:231-233` assumes `error.response` exists (`await response.text()`), so a
  network error becomes a TypeError; then in `packages/web-pkg/src/composables/webWorkers/pasteWorker/worker.ts:81-88`
  the catch block reads `e.response.headers` and throws again, so the item is neither in `successful` nor in `failed`.
  `useFileActionsPaste.ts:169` then calls `clearClipboard()` unconditionally.
- **Known issue check:** `--search "paste worker error"`, `"copy paste fails silently"` — nothing.
- **Severity guess:** Minor.

## H1-C4 Tiles view: Shift+ArrowUp after Shift+ArrowDown deselects the tile the cursor moves to

- **Steps**
  1. Folder with ≥ 15 files, tiles view (5 tiles per row at 1440 px).
  2. Click on empty space, press ArrowRight (first tile `f000` selected).
  3. Shift+ArrowDown twice -> `f000`…`f010` selected (correct).
  4. Shift+ArrowUp once.
- **Expected:** selection shrinks back to `f000`…`f005` (anchor to cursor, as after the first Shift+ArrowDown, and as the
  table view does).
- **Actual:** `f000`…`f004` selected; `f005` — the tile that now has the focus — is **not** selected ("5 selected").
  Symmetric case: after extending upwards, Shift+ArrowDown also drops the tile it lands on. Reproduced 2/2 (two runs
  after reload in `H1-14-tiles-shiftup.mjs`).
- **Screenshots:** `screens-raw/001-h1-14-run1-two-rows-down.png`, `screens-raw/002-h1-14-run1-one-up.png` (focus ring on
  unselected f005).
- **Console errors:** none.
- **Suspected cause:** `packages/web-app-files/src/composables/keyboardActions/useKeyboardFileNavigation.ts:237-245`
  (`handleTilesShiftUpAction`): the loop runs `i >= vp.nextIndex` and calls `removeSelection` for every `i` above the
  anchor — including `nextIndex`, the new cursor tile. Same in `handleTilesShiftDownAction` (:255-263) for `i <= nextIndex`
  below the anchor. The removal must stop before `nextIndex`.
- **Known issue check:** `--search "tiles shift arrow selection"`, `"Shift+ArrowUp"` — only admin-list / shift-click issues
  (#3738, #3741, #3678), not the tiles range shrink.
- **Severity guess:** Minor.

## H1-C5 Selection survives a page change; batch actions on page 2 also hit invisible items of page 1

- **Steps**
  1. Folder with > 20 files, table view, "Items per page" = 20.
  2. On page 1 tick `f001` and `f002` ("2 selected").
  3. Go to page 2 with the pagination. Nothing on the page is ticked, the app bar still says "2 selected".
  4. Tick `f021` ("3 selected") and click **Delete** in the app bar.
- **Expected:** a page change clears the selection (the header "select all" checkbox and Ctrl+A also work per page), or the
  app bar/delete clearly says that items on other pages are included.
- **Actual:** "3 items were moved to trash bin" — `f001` and `f002`, which are not visible on the current page, are
  deleted together with `f021` (WebDAV listing confirms: f001/f002/f021 gone). Same for Move to / Copy to / Download.
  Reproduced 2/2 (selection carry-over in both runs; delete run once, Undo is offered).
- **Screenshots:** `screens-raw/001-h1-18-page2-selection.png` ("2 selected", no visible row ticked),
  `screens-raw/002-h1-18-after-batch-delete-page2.png`.
- **Console errors:** none.
- **Suspected cause:** the selection lives in the resources store and is not reset on a `page` query change;
  `packages/web-pkg/src/composables/pagination/usePagination.ts:87-88` only derives the page from the route, nothing
  calls `resourcesStore.resetSelection()` when it changes (compare `useFileActionsDeleteResources.ts:57` which only
  fixes the page after deletion). Fix idea: reset the selection on page change, or show a "n selected on other pages" hint.
- **Known issue check:** `--search "selection page pagination"` — nothing.
- **Severity guess:** Minor / Question (could be intended multi-page selection, but nothing tells the user).
